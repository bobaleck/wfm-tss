ГОТОВЫЙ ЗАПРОС ДЛЯ ИИ-АГЕНТА НА PRODUCTION-СЕРВЕРЕ
==================================================

Перед отправкой желательно заменить значения в квадратных скобках. Если часть
данных ещё неизвестна, оставить как есть: агент должен задать один общий список
только действительно блокирующих вопросов и продолжить всё, что можно сделать
без них.

Скопируйте агенту весь текст ниже этой линии.
--------------------------------------------------------------------------

Ты находишься на новом production-сервере. Твоя задача — полностью развернуть
WFM Platform из GitHub, проверить её и оставить в рабочем, безопасном и
обслуживаемом состоянии.

Исходные данные владельца:

- домен: [WFM_DOMAIN или НЕТ_ДОМЕНА];
- email Let's Encrypt: [LETSENCRYPT_EMAIL или НЕТ];
- GitHub-доступ: [SSH_DEPLOY_KEY_УЖЕ_ДОБАВЛЕН / НУЖНО_СОЗДАТЬ_КЛЮЧ];
- первый admin-пароль: [ПЕРЕДАН_БЕЗОПАСНО / СГЕНЕРИРОВАТЬ];
- Naumen: [ПЕРЕДАНЫ_БЕЗОПАСНО / БУДУТ_ПОЗЖЕ];
- проекты: [СПИСОК или БУДУТ_ДОБАВЛЕНЫ_ПОЗЖЕ].

Репозиторий:
  git@github.com:bobaleck/wfm-tss.git
Ветка:
  main
Production-путь:
  /opt/wfm/app

ОБЯЗАТЕЛЬНЫЙ ПОРЯДОК РАБОТЫ

1. Сначала получи доступ к GitHub и клонируй ветку main в `/opt/wfm/app`.
   Если SSH-порт 22 заблокирован, используй официальный GitHub SSH endpoint на
   порту 443 по инструкции проекта. Никогда не отключай проверку host key.
2. Прочитай `/opt/wfm/app/project-map.txt` ПОЛНОСТЬЮ.
3. Затем прочитай `/opt/wfm/app/SERVER_DEPLOYMENT_AGENT.md` ПОЛНОСТЬЮ.
4. Считай эти два файла источником истины. Старые `DEPLOY.md`,
   `DEPLOYMENT.md` и `DEPLOY_AI_AGENT.md` использовать только как справку; при
   любом конфликте следуй `SERVER_DEPLOYMENT_AGENT.md`.
5. Выполняй развёртывание последовательно по каноническому runbook. После
   каждого этапа делай указанную там проверку. Не ограничивайся планом или
   советами — выполняй безопасные команды самостоятельно.

КРИТИЧЕСКИЕ ОГРАНИЧЕНИЯ

- Production WFM должна использовать PostgreSQL. Не использовать SQLite и не
  переносить `backend/wfm.db` с рабочего компьютера.
- Backend должен работать ровно в одном экземпляре и с `--workers 1`.
- PostgreSQL WFM должен быть доступен только локально; не открывай наружу 5432.
- FastAPI должен слушать `127.0.0.1:8000`; не открывай 8000 наружу.
- Снаружи разрешены только актуальный SSH-порт и Nginx 80/443.
- Историческая аналитика должна использовать общий PostgreSQL cache:
  TTL 600 секунд, retention 31 день.
- Проекты должны храниться в `tracked_projects`, сотрудники — в `employees`.
- Автосинхронизация сотрудников — раз в 60 минут, последовательно, только для
  не ручных проектов.
- «Мониторинг» должен оставаться live: current/recent endpoints и timeline с
  `hours` не должны получать данные из 10-минутного исторического cache.
- Скрытые подпроекты не должны присутствовать ни в фильтрах, ни в статистике.
- Naumen использовать только read-only. Не создавать UPDATE/INSERT/DELETE в
  Naumen и не менять существующие SQL-формулы без отдельного задания.
- Не устанавливать несколько backend workers и не поднимать второй экземпляр
  приложения на той же WFM-базе.
- Не применять `git reset --hard`, `git clean -fd`, force push или удаление
  production-данных.

СЕКРЕТЫ

- Не показывай в ответах и логах пароли, `.env`, JWT SECRET_KEY, GitHub token,
  приватные SSH-ключи, реквизиты Naumen, ФИО и логины сотрудников.
- Не добавляй секреты в Git и не передавай token прямо в URL репозитория.
- Если пароль admin надо сгенерировать, сохрани его только способом из runbook,
  с правами 0600. Сообщи владельцу, где безопасно его забрать, но не печатай
  значение в общий журнал/чат.
- Перед удалением bootstrap-файла дождись подтверждения владельца, что пароль
  сохранён и первый вход выполнен.

ЧТО ДОЛЖНО БЫТЬ СДЕЛАНО

- проверить ОС, ресурсы, DNS и системное время;
- установить необходимые пакеты из доверенных источников;
- создать отдельного системного пользователя `wfm`;
- настроить безопасный GitHub-доступ и зафиксировать фактический Git SHA;
- установить и настроить локальный PostgreSQL WFM;
- создать production `.env` без раскрытия секретов;
- установить backend-зависимости;
- выполнить compile, backend tests и `pip check`;
- создать актуальную схему WFM PostgreSQL, включая `analytics_cache`;
- создать и запустить systemd unit backend с одним worker;
- выполнить `npm ci` и production build frontend;
- настроить Nginx для SPA и `/api/` reverse proxy;
- включить firewall, не потеряв SSH-доступ;
- при наличии рабочего DNS выпустить TLS-сертификат и проверить renew;
- настроить ежедневный PostgreSQL backup и срок хранения;
- выполнить первый вход и первичную настройку проектов/сотрудников, если все
  реквизиты переданы;
- проверить health, login, проекты, роли, hidden, исторический cache и live
  Monitoring настолько, насколько позволяет доступ к Naumen;
- проверить перезапуск backend и переживание перезагрузки сервера systemd;
- оставить Git worktree чистым. `.env`, backup и generated frontend artifacts
  не должны попасть в commit.

ПРАВИЛА ПРИНЯТИЯ РЕШЕНИЙ

- Не спрашивай подтверждение для обычных безопасных шагов из runbook.
- Если отсутствует необязательная информация, продолжай всё, что от неё не
  зависит, и пометь соответствующий этап ожидающим.
- Остановись перед действием, которое может удалить/перезаписать существующие
  production-данные, изменить схему существующей базы без backup, раскрыть
  секрет или потребовать неизвестное значение от владельца.
- Если сервер не чистый, сначала выполни read-only аудит текущего состояния и
  не перезаписывай чужие файлы/службы.
- Если код расходится с документацией, не придумывай обход молча. Зафиксируй
  точное расхождение и выбери безопасный путь. Изменять source code во время
  обычного деплоя можно только при реальном блокере и после проверки diff.
- Если пришлось изменить код или инструкции, обнови `project-map.txt`, выполни
  все проверки, покажи diff владельцу и не публикуй изменения/force push без
  его явного разрешения.
- `WFM_instruction_pack` на production-сервере не требуется. Если задача
  внезапно потребует изменения SQL/метрик Naumen, останови эту часть: пакет
  должен быть передан отдельно.

УСЛОВИЯ ГОТОВНОСТИ

Работа не завершена, пока одновременно не выполнено следующее:

- PostgreSQL, backend и Nginx активны;
- frontend открывается по требуемому адресу;
- `/health` возвращает status=ok;
- health показывает analytics_cache enabled=true и backend=postgresql;
- backend tests и frontend build успешны;
- firewall не публикует 5432 и 8000;
- настроен и проверен backup;
- HEAD соответствует ожидаемому `origin/main`;
- рабочее дерево Git чистое;
- известные блокеры явно перечислены.

ИТОГОВЫЙ ОТЧЁТ

В конце дай владельцу короткий отчёт без секретов:

1. URL/IP и состояние HTTPS.
2. Полный опубликованный Git SHA.
3. Версии Python, Node.js и PostgreSQL.
4. Статусы PostgreSQL, wfm-backend и Nginx.
5. Результаты backend tests, frontend build и health.
6. Состояние analytics cache: enabled/backend/TTL/retention и время последнего
   обновления без вывода payload.
7. Только количества проектов и сотрудников, без персональных данных.
8. Время и путь последнего backup.
9. Что проверено в исторической аналитике и live Monitoring.
10. Что осталось заблокировано DNS/Git/Naumen/действиями владельца.
11. Где владельцу безопасно забрать временный admin-пароль и что bootstrap-файл
    нужно удалить после подтверждённого первого входа.

Начинай с проверки Git-доступа и чтения `project-map.txt`. Продолжай до полного
выполнения либо до конкретного внешнего блокера, который невозможно устранить
без владельца.
