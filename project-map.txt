4. АРХИТЕКТУРА ПРИЛОЖЕНИЯ
=========================

Frontend:
  React 18, TypeScript, Vite, React Router 6, React Query 5, Zustand,
  Tailwind CSS, Recharts, Axios, date-fns.

Backend:
  Python 3.11, FastAPI, SQLAlchemy, Pydantic, JWT, Uvicorn, psycopg2,
  pandas/openpyxl, APScheduler.

Хранилища:
  разработка на этом ПК: SQLite backend\wfm.db, не использовать как серверное
    хранилище и не добавлять в неё analytics_cache;
  production-сервер: PostgreSQL WFM (`WFM_DATABASE_URL`), проекты, сотрудники,
    настройки, графики и общий cache исторической аналитики;
  внешняя статистика: PostgreSQL Naumen/NCC (read-only, агенту недоступна);
  внешнее Naumen REST API: настройки/тест интеграции (агенту недоступно).

Поток запроса:
  Локально Browser :5173; production Browser :443 через Nginx
    -> frontend\src\api\client.ts
    -> Vite proxy /api локально или Nginx /api production
    -> FastAPI :8000/api/v1
    -> SQLAlchemy Session к WFM DB
    -> historical cached_call к PostgreSQL WFM
    -> при cache miss/refresh либо live — read-only psycopg2 к Naumen.

Особенности:
  - API сессия БД держится во время некоторых медленных вызовов Naumen;
  - пул SQLAlchemy расширен до pool_size=20/max_overflow=40;
  - исторический cache на production живёт в PostgreSQL и общий для всех;

  - `_sync_jobs` также живёт в памяти;

10. КАНОН КЛЮЧЕВЫХ МЕТРИК
=========================

Входящие:
  calls      = COUNT(*) выбранных вызовов;
  handled    = final_stage IN ('operator', 'redirect');
  lost       = final_stage = 'queue';
  ivr        = НЕ потеря, клиент не дошёл до очереди;
  phantom    = final_stage='queue' AND queue <= 5 секунд;
  comptarg   = handled в пределах per-queue answer_sec/calllimit;
  SL         = comptarg / (calls - phantlost - ivr) * 100;
  LCR        = (lost - phantlost) / calls * 100;
  AHT        = SUM(speaking + wrapup) / handled;
  hold       уже внутри speaking, повторно к AHT не прибавлять;
  оператор   только плечо dst_abonent_type='SP';
  end date   UI inclusive, SQL использует exclusive upper bound.

Единицы:
  в разных таблицах бывают ms и sec. Проверять словарь для каждой колонки;
  detail_outbound_sessions_ms — временные значения требуют особого внимания;
  не угадывать единицы по имени.

Статусы:
  проектные нестандартные статусы классифицируются через status_configs;
  standard work/offline определены в status_classification.py;
  «активный» нельзя считать простым status != offline;
  длительность безопаснее считать через LEAD и границы окна.

Исходящие:
  контакт в текущем коде = speaking_time > 10 секунд;
  бизнес-результат кейса — по последней попытке;
  project_id и partneruuid нельзя смешивать;
  dosm/attempt_result сверять с правилами 05/09.

Любое изменение этих формул требует:
  адресного чтения instruction pack;
  теста;
  отметки «нужна живая проверка куратором»;
  обновления project-map.txt.


11. ОСОБАЯ ЛОГИКА HIDDEN
========================

Хранение:
  входящая очередь: queue_settings.queue_name = точное имя;
  исходящий подпроект: queue_name = 'out:' + project_uuid;
  hidden=true означает исключить из фильтров И статистических расчётов.

    GET /analytics/queues
    GET /analytics/outbound-projects
    -> только видимые;
  страница настроек:
    те же endpoints с include_hidden=true
    -> полный список, чтобы скрытый элемент можно было вернуть.

Backend:
  analytics.py вычисляет hidden names/ids;
  naumen_db.py добавляет фильтр в каждую статистическую функцию;
  пустой список outbound ids означает «ничего», а не «все»;
  cache key включает hidden/project filter.

Frontend:
  ProjectSettingsPage использует include_hidden=true и отдельный query key;
  аналитические фильтры получают только видимое;
  после save инвалидируется весь React Query cache проекта.

Тест:
  backend\tests\test_hidden_filters.py
  покрывает SQL-фильтры, пустой outbound filter и различие analytics/settings.


12. БЕЗОПАСНОСТЬ И РИСКИ
========================

Обязательные правила:
  - не логировать JWT/Authorization даже частично;
  - не печатать .env и integration_settings;
  - все SQL values передавать параметрами psycopg2;
  - f-string допустим только для константного фрагмента SQL, выбранного кодом;
  - проверять project scope на backend;
  - FIRST_ADMIN_PASSWORD задаёт только первого admin и не выводится в лог;
  - SECRET_KEY/FIRST_ADMIN_PASSWORD в production обязательно менять.

Известные ограничения, не исправлять вслепую:
  1) integrations.py для теста REST создаёт SSL context с CERT_NONE.
     Причиной может быть частный сертификат. Правильное решение — доверенный CA,
     но переключение требует проверки реальной инфраструктуры.
  2) naumen_db.py использует `status_changes` во многих функциях, хотя пакет
     рекомендует `status_changes_ms`. Массовая замена требует живой проверки.
  3) APScheduler, `_sync_jobs`, refresh registry и вспомогательные live-карты
     требуют одного backend worker. Исторические payload при этом общие в
     PostgreSQL.
  4) production `npm audit --omit=dev` после коммита e61a15b оставлял две
     moderate advisory React Router; автоматическое полное исправление могло
     потребовать breaking upgrade Router/Vite. Перед будущим upgrade проверить
     актуальный audit и миграционные notes.
  5) Vite production bundle около 1.06 MB и выдаёт warning >500 KB; это не
     функциональная ошибка, оптимизировать отдельной задачей.
  6) `create_all` создаёт новые PostgreSQL-таблицы, но не ALTER существующих
     колонок. Перед будущим production update с изменением моделей нужен backup
     и release-specific migration; подробнее SERVER_DEPLOYMENT_AGENT.md.

17. ДЕПЛОЙ
===========

Основной и канонический документ для чистого production:
  wfm-telesales\SERVER_DEPLOYMENT_AGENT.md

Старые DEPLOY_AI_AGENT.md / DEPLOY.md / DEPLOYMENT.md оставлены как справка и
должны направлять к каноническому документу.

Ключевые условия:
  - рабочий путь в документации: /opt/wfm/app;
  - backend ровно 1 worker;
  - PostgreSQL только на production-сервере; локальную wfm.db не переносить;
  - секреты только в environment file;
  - WFM_DATABASE_URL, не DATABASE_URL;
  - analytics_cache: PostgreSQL-only, TTL 600 sec, retention 31 days;
  - employees: initial ручной sync, затем server scheduler каждые 60 минут;
  - monitoring current/recent endpoints обходят исторический cache;
  - frontend собирается npm run build и отдаётся Nginx;
  - перед деплоем backup WFM DB;
  - после деплоя health, login, project selection, основные страницы;
  - живые Naumen-метрики проверяет пользователь/куратор в своей сети;
  - WFM_instruction_pack на сервер для обычного деплоя не требуется.


18. ПРОТОКОЛ ОБНОВЛЕНИЯ ЭТОЙ КАРТЫ
=================================

После изменения кода или инструкций агент обязан:
  1) определить затронутые разделы project-map.txt;
  2) обновить маршрутизацию задачи, пути и правила;
  3) если изменён frontend route — обновить раздел 6;
  4) если изменён API — обновить раздел 7;
  5) если изменена модель/миграция/смысл таблицы — обновить раздел 8 и повторить
     read-only integrity snapshot;
  6) если изменена инструкция/формула — обновить разделы 3, 9 и 10;
  7) если изменены security/deps/ограничения — обновить раздел 12;
  8) если изменены команды запуска/test/deploy/Git — обновить 13–17;
  9) поставить новую дату версии в начале файла;
 10) проверить, что пути существуют и старые указания удалены.

Если правка не меняет карту (например, исправлена опечатка в подписи), агент
всё равно должен проверить project-map.txt и в итоговом ответе явно сказать,
что карта проверена и смысловых изменений для неё нет.

Запрещено:
  - оставлять в карте заведомо устаревший маршрут «на потом»;
  - копировать секреты или персональные данные;
  - превращать карту в журнал всех коммитов;
  - дублировать здесь весь instruction pack;
  - возвращать файл fast-links-ft.txt;
  - выносить project-map.txt из Git-репозитория.
